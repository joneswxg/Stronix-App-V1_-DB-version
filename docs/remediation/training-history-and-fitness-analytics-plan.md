# Stronix 训练历史与体测分析整改计划

> 状态：待实施
>
> 编制日期：2026-08-03
>
> 范围：训练历史、动作进步、训练负荷、肌群训练量、体成分趋势与恢复记录。

## 1. 背景与目标

Stronix 已能保存训练主记录、动作组明细和身体测量记录，并向用户展示日历、单次训练详情、基础训练统计和体测趋势。

当前能力更接近“训练日志”：用户能看到自己何时训练、练了什么、完成了多少容量，但系统尚不能稳定回答以下问题：

1. 我是否按计划、以稳定节奏完成训练？
2. 我的训练负荷是在合理递增，还是过快增加或明显下降？
3. 某个动作的力量、次数和训练容量是否持续进步？
4. 我的体重、体脂和肌肉变化是否符合减脂、增肌或力量目标？
5. 我今天是否适合加量，还是需要降低负荷、休息或调整训练部位？

本计划的目标不是增加大量孤立图表，而是建立可信、统一、可解释的训练—体成分—恢复数据闭环。

## 2. 当前基础与主要问题

### 2.1 已有基础

当前数据库已经保存了完成分析所需的一部分核心数据：

- `training_history`：用户、计划、训练日期、总容量、训练时长、备注等训练主记录。
- `training_history_details`：动作、组号、重量、次数、左右重量、是否完成、难度、备注、双侧记录标识等组明细。
- `body_measurements`：体重、身高、体脂率、骨骼肌量、内脏脂肪等级和测量日期。
- 动作目录及目标肌群/部位关系：可作为肌群训练量统计的基础。

主要 schema 参见：

- `tools/database/schema/baseline.sql:223-255`
- `tools/database/schema/baseline.sql:257-269`

当前 UI 已提供：

- 历史日历、按日训练记录列表、单次训练详情和编辑。
- 本月/本年总容量、总时长、训练次数、训练天数及趋势图。
- 训练中的最近 5 次动作历史。
- 体重、骨骼肌量、体脂率、BMI、体脂肪重量、BMR 等体测趋势。

### 2.2 必须优先整改的问题

1. **动作历史缺少用户隔离。**
   `SQLiteActionHistoryRepository` 按动作查询历史时未以 `user_id` 过滤，多个账户共用本地数据库时可能读到其他用户数据。此项同时是隐私与正确性问题。

2. **训练容量统计口径不统一。**
   训练完成时正确将双侧动作计算为 `(left_weight + right_weight) × reps`；但动作进步和部分部位统计按 `weight × reps` 聚合，会遗漏双侧动作，造成主历史、动作历史和肌群统计不一致。

3. **部位统计存在聚合风险，当前不宜直接开放。**
   当前周统计将训练主表与明细表 JOIN 后再累计主表的容量与时长，可能按明细行重复累计。同一领域的月查询还存在动作部位字段命名不一致问题。

4. **计划使用率的百分比计算不具备业务含义。**
   当前代码将计划容量除以 100 作为百分比。应明确是“训练次数占比”还是“训练容量占比”，并以全部计划的相应总值为分母。

5. **部分已有统计未被展示或解释。**
   `streak_days`、计划使用情况、动作进步数据已有服务层基础，但未形成历史页内可理解、可行动的用户界面。

6. **恢复没有可持久化数据模型。**
   现有组间休息倒计时仅是训练中内存状态；没有睡眠、疲劳、酸痛、疼痛、HRV、静息心率或训练准备度记录。

## 3. 整改原则

### 3.1 先可信，后丰富

任何新图表、PR 或推荐都必须先使用同一份可测试的计算规则。不得让训练详情、统计页、动作历史和肌群分析各自重复编写容量公式。

### 3.2 优先提供可行动结论

优先展示能影响下一次训练决策的内容，例如：完成率、当前动作表现、近周期负荷变化、肌群训练量和体重变化速率；不优先做缺少解释的大型仪表盘。

### 3.3 以趋势而非单点判断

体重、体脂率、骨骼肌量及 BMR 都会受到测量条件影响。界面应强调 7/14 日移动平均和 2–4 周趋势，不把单次波动解释为真实组织变化。

### 3.4 恢复建议保持非医疗定位

恢复模块应使用“今日训练准备度”或“自我恢复状态”等措辞，提供保守的训练调整提醒；不进行医学诊断，不声称可以诊断过度训练、伤病或疾病。

### 3.5 保持低输入负担

第一版恢复记录应能在 10–15 秒内完成。优先采用睡眠、疲劳、酸痛和疼痛等主观数据，穿戴设备数据作为后续可选能力。

## 4. 数据定义与统一口径

## 4.1 完成组和训练容量

定义：只有 `is_completed = true` 的训练组进入训练负荷、动作进步和肌群训练量计算。

标准容量公式：

```text
普通动作组容量 = weight × reps
双侧动作组容量 = (left_weight + right_weight) × reps
训练容量 = 所有已完成组容量之和
```

处理规则：

- 重量、次数或双侧重量缺失时，不静默当作零；返回可诊断的缺失状态，供 UI 显示“数据不完整”。
- `weight_unit` 在第一阶段固定为 kg；若未来支持 lb，必须在聚合前标准化为 kg。
- 单次训练主记录的 `volume` 是快照值；分析模块可从详情重算并校验，发现差异时记录诊断而不是直接覆盖历史数据。

## 4.2 有效训练组

第一版采用透明、易理解的规则：

- 已完成组；
- 次数范围为 6–30；
- 主目标肌群计 1 组；
- 次要肌群如需统计，计 0.5 组，并在 UI 说明该规则；
- 不将单纯的 kg 容量等同于肌肉刺激。

未来引入 RIR/RPE 后，再对接近力竭的组进行更细粒度区分。

## 4.3 动作进步与个人记录

对每个动作、每次训练计算：

- 最大完成重量；
- 最大完成次数；
- 动作训练容量；
- 估算 1RM（只用于 1–10 次完成组）；
- 左/右最大重量、左右差值及趋势（双侧动作）。

建议采用 Epley 估算 1RM：

```text
e1RM = weight × (1 + reps / 30)
```

个人记录必须分类型呈现，不使用模糊的单一“最佳记录”：

- 最大重量 PR；
- 最大次数 PR；
- 最大估算 1RM PR；
- 单次动作容量 PR。

## 4.4 周期比较

默认比较范围：

- 最近 7 天 vs 前 7 天；
- 最近 28 天 vs 前 28 天；
- 本月 vs 上月；
- 自定义日期范围。

对空周期、零训练量、同一周期重叠等情况必须有明确状态，不得产生除零、无穷大或误导性的百分比。

## 4.5 体成分趋势

建议计算：

```text
体脂肪重量 = 体重 × 体脂率 / 100
去脂体重 = 体重 × (1 - 体脂率 / 100)
每周变化率 = (周期末移动平均 - 周期初移动平均) / 周数
```

展示规则：

- 默认优先展示 7 日移动平均；体测频率不足时退化为可用测量点，并明确提示。
- 对体脂率和骨骼肌量显示“建议在相同时间、进食和水合条件下测量，重点观察 2–4 周趋势”。
- BMR 是由体测数据推导的估算值，不应作为独立测量结果描述。

## 5. 分阶段实施计划

## 阶段 0：数据正确性、隐私隔离与测试底座

### 目标

保证所有历史分析结果只属于当前用户，且容量、日期和聚合口径可靠可复用。

### 整改项

1. 修复动作历史查询：所有 `training_history_details` 与 `training_history` 的读取必须以当前 `user_id` 过滤。
2. 提取 `TrainingVolumeCalculator`（或等价领域服务），集中计算普通/双侧动作完成组容量。
3. 使用动作 ID 而非动作名称模糊匹配作为进步统计主键；名称仅用于展示。
4. 修正计划使用率，明确提供：
   - `sessionShare`：该计划训练次数 / 总训练次数；
   - `volumeShare`：该计划容量 / 总训练容量。
5. 暂不解除部位统计 UI 注释；先重写查询，避免 JOIN 放大训练主表容量/时长。
6. 为所有分析查询增加当前用户和日期范围过滤，并限制分页、排序与无数据状态。
7. 为容量、百分比、日期边界、双侧动作、跨用户隔离建立单元测试和 Repository 集成测试。

### 重点文件

- `Stronix-App/Sources/Services/Local/ActionHistoryRepository.swift`
- `Stronix-App/Sources/Services/Local/LocalTrainingHistoryService.swift`
- `Stronix-App/Sources/Services/Local/TrainingHistoryRepository.swift`
- `Stronix-App/Sources/Services/Local/TrainingSessionManager.swift`
- `Stronix-App/Tests/`

### 验收标准

- 任意动作历史、训练详情和统计查询均不能返回其他用户的记录。
- 普通与双侧动作在主记录、动作记录和统计中的容量一致。
- 未完成组不进入训练容量、有效组、PR 或肌群统计。
- 计划次数占比与容量占比分别以正确分母计算，总和在合理误差内为 100%。
- 部位统计的容量/时长不会因动作明细 JOIN 被重复累计。
- 测试覆盖零数据、空值、同日多次训练、跨月范围、夏令时/时区边界和双侧动作。

## 阶段 1：训练概览与依从性

### 目标

让用户一眼了解“我近期练得是否稳定、是否完成计划、负荷是否明显变化”。

### 功能范围

在历史 Tab 的统计页增加时间范围：最近 7 天、最近 28 天、本月、上月、自定义日期。

新增指标：

- 训练天数；
- 训练次数；
- 总训练时长；
- 总训练容量；
- 单次平均时长；
- 单次平均容量；
- 与前一等长周期的变化；
- 最近一次训练日期；
- 计划完成率；
- 当前周期训练频率。

### 计划完成率

```text
组完成率 = 已完成组数 / 计划组数 × 100%
动作完成率 = 至少完成一组的动作数 / 计划动作数 × 100%
```

页面应在单次训练详情、计划汇总和周期统计中分别呈现，不将“训练时长”误作完成质量。

### UX 建议

优先用短结论辅助数值，例如：

- “过去 7 天完成 3 次训练，与前 7 天持平。”
- “计划 A 的组完成率为 91%，表现稳定。”
- “本周期训练容量较前一周期增加 8%，属于温和递增。”

不将“连续每天训练”作为主要成就。力量训练需要恢复，默认更强调周训练频率、计划完成率和节奏稳定性。

### 验收标准

- 所有范围均能正确处理零训练数据。
- 周期比较的起止日期不重叠，且在本地日历语义下稳定。
- 图表与指标使用同一聚合数据源，点击图表后显示的值与汇总一致。
- 训练天数按不同训练日期计数，而不是按训练记录数计数。

## 阶段 2：动作进步与渐进超负荷

### 目标

把“最近 5 次记录”升级为可解释的动作进步页面，使用户知道是否应加重量、维持或调整次数。

### 功能范围

1. 在历史 Tab 增加“动作进步”入口；训练中动作卡的“历史”入口可跳转或展开同一数据视图。
2. 每个动作显示：
   - 最近表现；
   - 最大重量、最大次数、e1RM、动作容量的 PR；
   - 最近 4–8 次训练趋势；
   - 最近一次与上一次的差异；
   - 双侧动作的左/右趋势及差异。
3. 支持按动作 ID、日期范围和训练计划过滤。
4. 对 1–10 次范围外的组明确不计算 e1RM，避免高次数估算误导。
5. 在引入 RIR 前，只给出谨慎规则提示，不作强制推荐：
   - 多次达到目标次数上限，可提示“下次可考虑小幅加重”；
   - 多次低于目标次数下限，可提示“保持重量、增加恢复或适当降低负重”。

### RIR/RPE 数据准备

新增组明细可选字段时优先选 RIR：

- `rir INTEGER NULL CHECK (rir BETWEEN 0 AND 5)`；
- 保留空值以兼容未填写的旧训练；
- UI 使用“还能完成几次”帮助文案，而非仅展示抽象评分。

RPE 只能在明确换算或用户选择时派生，不应与 RIR 混作同一字段。

### 验收标准

- PR 按类型独立计算，不能把最大重量误称为最佳表现。
- 双侧动作不丢失左/右数据，也不以单侧重量错误替代总容量。
- 所有趋势只使用当前用户、已完成组和有效日期范围。
- e1RM 不对零重量、缺失次数、超过定义次数范围的组计算。
- 页面能解释数据不足状态，例如“至少还需 2 次记录以显示趋势”。

## 阶段 3：肌群训练量与训练平衡

### 目标

帮助用户发现训练量不足、失衡或连续高负荷刺激的肌群。

### 功能范围

1. 修复并开放身体部位/目标肌群统计入口。
2. 按最近 7 天、28 天和自定义周期展示：
   - 每个主要肌群有效组数；
   - 训练频率；
   - 训练容量；
   - 最近训练日期；
   - 推/拉/腿训练量概览；
   - 左右侧容量及差异（适用时）。
3. 将动作到目标肌群的关系作为唯一归因来源，明确主/次目标肌群的计数权重。
4. 首版不对用户宣称“最佳周组数”；只提供与用户自身近期均值、设定目标或计划目标的比较。

### 技术要求

- 不使用 `SUM(training_history.volume)` 作为 JOIN 后的肌群容量；应从已完成组明细按统一容量计算聚合。
- 对一个动作关联多个肌群时，根据主/次目标权重分摊或分别计组；规则必须公开且可测试。
- 按动作 ID 与肌群关系连接，不能依赖展示名称。

### 验收标准

- 一次训练包含多个动作时，训练时长和容量不会因 JOIN 被重复计数。
- 肌群组数可追溯到具体动作和组明细。
- 动作没有有效肌群映射时，显示“未分类”，不静默归入任意部位。
- 用户能从肌群卡片进入对应动作明细。

## 阶段 4：体成分目标与训练关联

### 目标

让用户从“查看体测数据”转向“理解体重变化质量及其与训练的关系”。

### 功能范围

1. 增加目标设置：减脂、增肌、力量、维持；允许用户设置体重或体脂方向性目标。
2. 在体测概览优先显示：
   - 体重 7/14 日移动平均；
   - 体脂肪重量；
   - 去脂体重或骨骼肌量；
   - 2/4 周平均变化率；
   - 距离目标的趋势，而非虚假的固定进度条。
3. 在训练统计周期中增加体成分摘要：
   - 周期体重变化；
   - 体脂肪重量变化；
   - 骨骼肌量/去脂体重变化；
   - 同期训练频率和容量变化。
4. 显示测量质量提示：同一时间、同一水合/进食条件下测量；体脂与肌肉重点看 2–4 周趋势。
5. 将营养计算器默认值改为读取用户资料和最新体测（需用户确认），并允许用户选择是否保存每日目标；不把估算值当作医学建议。

### 数据模型调整

保留原始体测记录，同时可增加：

- `measurement_source`：手动、智能体脂秤、HealthKit 等；
- `measurement_conditions_note`：可选简短备注；
- `goal_type`、`target_weight_kg`、`target_body_fat_percentage`、`target_date`：单独的目标表或用户目标表。

体测目前按本地日期归一化。如果产品继续采用“每日一次趋势”的语义，应在 UI 上明确同日多次记录的处理策略：覆盖、保留并选择最后一次，或计算日汇总；不要让录入顺序暗中改变趋势含义。

### 验收标准

- 移动平均对数据不足、同日重复记录和日期缺口有确定行为。
- 体脂肪重量、去脂体重、BMI、BMR 均有独立公式测试。
- 不再使用硬编码数值渲染“健康进度条”。
- 所有体测建议均显示为趋势观察或一般训练建议，避免医学诊断用语。

## 阶段 5：恢复与训练准备度闭环

### 目标

在不增加过度填写负担的前提下，提供保守、可解释的恢复状态提示。

### 最小可行数据模型

新增每日恢复记录表，建议字段：

| 字段 | 类型/范围 | 说明 |
| --- | --- | --- |
| `id` | 主键 | 恢复记录标识。 |
| `user_id` | 外键 | 所有记录按用户隔离。 |
| `record_date` | 本地业务日期 | 每日一条，建议 `(user_id, record_date)` 唯一。 |
| `sleep_duration_minutes` | 可空非负整数 | 睡眠时长。 |
| `sleep_quality` | 可空 1–5 | 主观睡眠质量。 |
| `fatigue` | 可空 1–5 | 主观疲劳。 |
| `stress` | 可空 1–5 | 主观压力。 |
| `training_readiness` | 可空 1–5 | 训练意愿/准备度。 |
| `soreness` | 可空 0–10 | 全身酸痛；肌群明细后续独立建表。 |
| `pain_level` | 可空 0–10 | 不适风险提示，非诊断。 |
| `note` | 可空文本 | 旅行、加班、感冒等背景。 |
| `created_at` / `updated_at` | 时间 | 审计字段。 |

可选的第二阶段扩展：

- 按肌群记录酸痛和疼痛；
- Apple Health / HealthKit 的睡眠、静息心率、HRV；
- 数据来源、授权状态、最近同步时间。

### 规则型建议

第一版只提供规则驱动、可解释的提示：

- 睡眠、疲劳或准备度连续偏低：提示维持训练重量、缩短训练或安排轻量日。
- 特定肌群酸痛较高且最近刚完成高训练量训练：提示今天优先训练其他部位。
- 疼痛持续、加重或影响动作完成：提示停止引发疼痛的训练动作，并咨询医疗或运动康复专业人士。
- 恢复数据缺失：展示“尚未记录今日恢复状态”，不猜测用户状态。

不应将上述规则包装成医学恢复评分、伤病诊断或自动处方。

### 验收标准

- 恢复记录严格按用户和日期隔离。
- 用户可跳过任意恢复字段，不阻塞训练。
- 建议可回溯至具体输入和规则，不能是黑盒分数。
- 疼痛相关文案包含非医疗声明和明确的升级建议。
- HealthKit 为可选授权，不授权时核心训练功能不受影响。

## 6. 数据库迁移与兼容策略

所有新增字段和表必须通过 `DatabaseLifecycle` 的增量 migration 机制演进，不得覆盖或重建用户 Documents 数据库。

每次 migration 至少应包含：

1. 稳定、不可变的 migration ID；
2. 正向 SQL 与必要索引；
3. 数据回填策略或明确的空值兼容规则；
4. 迁移后 schema、integrity、foreign key 验证；
5. 失败事务回滚与备份恢复测试；
6. 对旧历史缺少新字段的 UI 降级策略。

建议的迁移顺序：

1. 修复/补充训练历史唯一性和查询索引（如确认现有并发风险后实施）；
2. 新增 RIR 可空字段；
3. 新增用户训练目标表；
4. 新增体测来源/条件字段；
5. 新增每日恢复记录表；
6. 按肌群恢复明细和 HealthKit 元数据作为后续独立 migration。

不应为分析便利修改既有训练历史快照。新增分析应优先从历史详情推导，并允许旧记录缺少 RIR、恢复或测量来源字段。

## 7. 测试与质量门槛

### 7.1 单元测试

至少覆盖：

- 普通、双侧、未完成、缺失值组的容量计算；
- 有效训练组判定；
- e1RM 的次数边界；
- PR 分类与并列记录；
- 周期比较、零分母和日期范围；
- 体脂肪重量、去脂体重、移动平均和变化率；
- 恢复规则与风险提示阈值。

### 7.2 Repository 与集成测试

至少覆盖：

- 多用户数据库的严格数据隔离；
- 同日多次训练、跨月/跨年范围、空数据；
- JOIN 不重复累计训练主记录；
- 动作 ID 到肌群映射缺失/多映射；
- 新旧 schema 下的历史读取；
- migration 后旧历史仍可读取，缺失新字段时 UI 正确降级。

### 7.3 UI 与手动回归

至少验证：

- 历史日历、按日列表、详情、编辑和删除；
- 训练完成后统计、动作进步和肌群数据同步；
- 双侧动作展示、容量和左右趋势；
- 体测新增/编辑/删除后移动平均和目标进度更新；
- 无数据、数据不足、无权限、查询失败和恢复字段缺失状态；
- Dynamic Type、中文文案、深色模式和图表无障碍描述。

## 8. 发布顺序与依赖关系

```text
阶段 0：数据正确性与计算内核
  └─ 阶段 1：训练概览与完成率
       ├─ 阶段 2：动作进步与 PR
       └─ 阶段 3：肌群训练量与平衡
            └─ 阶段 5：恢复与准备度

阶段 4：体成分目标与训练关联
  └─ 可与阶段 2/3 并行，但依赖统一日期和趋势计算工具
```

建议先完成阶段 0，再在阶段 1 和阶段 2 中选择一个用户价值最高的垂直切片发布。对多数力量训练用户，推荐优先顺序为：

1. 阶段 0；
2. 阶段 1 的完成率与周期比较；
3. 阶段 2 的动作进步与 PR；
4. 阶段 4 的体成分目标；
5. 阶段 3 的肌群分析；
6. 阶段 5 的恢复闭环。

## 9. 非目标与边界

本计划不包括：

- 医疗诊断、伤病诊断、治疗建议或临床恢复评分；
- 将估算 BMR、体脂秤结果或 e1RM 作为精确医学测量；
- 未经用户授权自动读取健康数据；
- 第一版就构建不可解释的 AI 推荐或黑盒训练处方；
- 为追求指标数量而展示无法改变用户下一步行为的统计图。

## 10. 完成定义

该整改计划完成后，用户应能够在不理解复杂训练术语的前提下，从历史功能中得到可信答案：

- 我近期训练是否稳定、是否完成计划；
- 哪些动作在变强，下一次是否适合加重或维持；
- 哪些肌群训练量偏低、偏高或间隔不足；
- 体重变化主要是脂肪、肌肉还是短期波动；
- 今日恢复记录是否提示应保守训练；
- 所有结论都能回溯到自己的训练、体测或恢复数据，并有明确的计算口径。
