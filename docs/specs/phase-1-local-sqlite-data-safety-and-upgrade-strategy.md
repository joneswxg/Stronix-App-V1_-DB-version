# Phase 1 Spec：本地 SQLite 数据安全与升级策略

> GitHub Issue: https://github.com/joneswxg/Stronix-App-V1_-DB-version/issues/1
>
> 数据处置决策（2026-07-20）：当前整改期项目数据库中的全部既有数据均可删除，不要求迁移或保留。Phase 1 可以直接重建 Bundle DB、开发环境 Documents DB 和目标 schema。该授权仅适用于本次整改前已经存在的项目数据；整改完成后产生的真实用户数据仍必须通过安全、增量的 migration 生命周期得到保护。

## Problem Statement

Stronix App 当前使用同一个本地 SQLite 数据库承载内置动作、Template Plan、账号、User Plan、训练历史和体测等内容。现有数据库结构存在外键未启用、错误外键目标、以 `user_id = 0` 表示 Template Plan、孤儿动作关系、版本来源漂移和单复数表名混用等问题。

当前升级机制会在 Bundle DB 较新时备份并删除 Documents DB，再复制整套 Bundle DB。这种机制没有区分内置数据与未来真实用户数据。虽然本次整改前的现有数据库数据已经确认可以全部删除，但如果继续保留该升级机制，整改完成后的应用升级仍可能覆盖真实用户的 User Plan、训练历史、体测和账号数据。

项目也缺少独立、可追踪、可重复执行的 schema migration 机制。应用版本、数据库版本和实际 schema 状态之间没有可靠的一一对应关系；迁移失败、App 降级和 WAL 模式下的备份恢复也没有明确保证。

因此，Phase 1 不需要为当前脏数据设计昂贵的兼容迁移。它需要利用“当前数据可删除”的窗口直接建立干净目标 schema，同时建立整改完成后长期使用的安全数据库生命周期，确保未来 schema 升级不会再依赖整库覆盖。

## Solution

Phase 1 采用“当前一次性重建，未来增量迁移”的双层策略。

对于本次整改前的数据库，直接删除全部既有行和不合格结构，根据目标模型重新创建 Bundle DB、开发环境 Documents DB 和必要的种子数据。当前错误外键、`user_id = 0`、孤儿动作和历史脏数据不做逐行修复、隔离或兼容迁移；它们通过重建数据库被一次性清除。

新的目标 schema 从一开始就分离 Template Plan 与 User Plan，使用真实外键并遵循 Plural Table Names。需要保留的产品资产仅包括经过校验的内置动作目录、Template Plan 定义及其他明确的种子内容；这些内容应从受版本控制的种子来源重新生成，而不是从当前脏数据库复制。

同时建立统一的本地数据库生命周期入口。它在应用业务功能开放前完成数据库定位、首次初始化、连接 PRAGMA、schema ledger 检查、未来 migration、备份恢复、迁移后验证和结构化诊断。整改完成后，已有 Documents DB 被视为未来真实用户数据的权威副本，正式升级不得再通过删除并复制 Bundle DB 的方式更新。

主要自动化测试只跨越一个最高层接缝：数据库生命周期入口。测试通过隔离目录验证干净初始化、当前版本启动、合成旧 schema 升级、重复启动、失败回滚和 schema 过新等外部行为。内部 migration 实现细节不成为公共测试接口。

## User Stories

1. 作为项目维护者，我希望可以删除当前整改前数据库中的全部数据，以便无需为无保留价值的脏数据承担兼容迁移成本。
2. 作为项目维护者，我希望当前数据库通过干净重建达到目标 schema，以便历史外键错误不会被带入新底座。
3. 作为项目维护者，我希望当前 `user_id = 0` Template Plan 数据可以直接删除，以便不再维护虚构用户语义。
4. 作为项目维护者，我希望当前孤儿计划动作和组数据可以直接删除，以便无需设计恢复或隔离流程。
5. 作为项目维护者，我希望当前账号、User Plan、训练历史和体测数据可以直接删除，以便 Phase 1 优先建立正确模型。
6. 作为项目维护者，我希望内置动作和 Template Plan 从经过校验的种子来源重新生成，以便目标数据库不复制当前脏数据。
7. 作为项目维护者，我希望一次性重建动作是明确的整改步骤，而不是每次 App 升级都会触发的行为，以便破坏性操作不会长期存在。
8. 作为新用户，我希望首次安装时自动获得可用的内置动作和 Template Plan，以便无需网络即可开始使用应用。
9. 作为新用户，我希望首次创建的本地数据库已经符合目标 schema，以便不会先创建旧结构再立即迁移。
10. 作为整改完成后的用户，我希望未来 App 升级不会删除或覆盖我的 Documents DB，以便 User Plan、历史和体测长期保留。
11. 作为整改完成后的用户，我希望未来 schema 升级在原数据库上增量执行，以便新版本能够演进而不替换用户数据。
12. 作为整改完成后的用户，我希望 migration 失败时原数据库能够恢复，以便升级失败不会造成数据丢失。
13. 作为整改完成后的用户，我希望备份失败时 migration 不开始，以便数据库不会在没有恢复点时被修改。
14. 作为整改完成后的用户，我希望多次启动同一版本不会重复迁移，以便数据和 schema 保持稳定。
15. 作为整改完成后的用户，我希望 App 降级遇到更新 schema 时不会尝试破坏性降级，以便较新版本产生的数据得到保护。
16. 作为用户，我希望应用只在数据库准备成功后开放计划、训练、历史和体测功能，以便业务不会访问半初始化数据库。
17. 作为用户，我希望数据库准备失败时看到明确错误状态，以便不会把空页面误认为数据已经消失。
18. 作为用户，我希望短暂数据库锁竞争不会立即导致保存失败，以便本地写入更加稳定。
19. 作为用户，我希望 Template Plan 可以正常浏览和复制，以便使用内置训练方案作为起点。
20. 作为用户，我希望复制 Template Plan 后得到独立的 User Plan，以便自由编辑自己的训练内容。
21. 作为用户，我希望编辑 User Plan 不会修改 Template Plan，以便模板内容保持稳定。
22. 作为用户，我希望 User Plan 只能归属于真实用户，以便计划所有权明确。
23. 作为用户，我希望计划列表中的动作数量与计划详情一致，以便数据库关系不会产生矛盾展示。
24. 作为用户，我希望完成训练后历史和 User Plan 关系正确，以便训练记录能够可靠读取。
25. 作为维护者，我希望所有正常业务连接明确开启外键约束，以便无效关系不能重新进入数据库。
26. 作为维护者，我希望所有正常业务连接设置统一的 busy timeout，以便锁等待行为一致。
27. 作为维护者，我希望 WAL 模式与备份策略共同设计，以便并发稳定性不会破坏恢复能力。
28. 作为维护者，我希望 schema 版本独立于 App 营销版本和构建号，以便数据库演进可以准确追踪。
29. 作为维护者，我希望每个 migration 都具有稳定且不可修改的标识，以便未来不同安装实例得到一致结果。
30. 作为维护者，我希望 migration 按固定顺序执行，以便依赖关系清晰。
31. 作为维护者，我希望只有成功提交的 migration 才写入 ledger，以便记录与真实 schema 一致。
32. 作为维护者，我希望 migration 完成后自动验证 integrity 和外键，以便不合格数据库不会被标记为 ready。
33. 作为维护者，我希望 schema 高于 App 支持版本时返回明确状态，以便不会静默覆盖或降级。
34. 作为维护者，我希望数据库诊断包含路径、schema version、foreign key 状态、journal mode 和 migration 摘要，以便快速定位启动问题。
35. 作为维护者，我希望诊断不包含密码、验证码和用户训练明细，以便日志不泄露敏感数据。
36. 作为开发者，我希望业务 Service 只获取准备完成的连接，以便不自行处理复制、迁移或恢复。
37. 作为开发者，我希望新增 schema 变化只需增加 migration，以便不再修改 Bundle DB 后整库覆盖。
38. 作为开发者，我希望 Template Plan 与 User Plan 使用独立结构，以便 Phase 3 可以基于稳定模型重构计划域。
39. 作为开发者，我希望新表从一开始使用 Plural Table Names，以便数据库命名不再继续漂移。
40. 作为开发者，我希望强制重建只存在于显式整改工具或 DEBUG 工具中，以便正式启动路径不能误触发。
41. 作为测试者，我希望测试使用临时目录，以便不会修改模拟器或开发者的真实 Documents DB。
42. 作为测试者，我希望一次生命周期调用即可验证初始化、迁移和恢复，以便测试贴近真实启动行为。
43. 作为测试者，我希望使用合成用户数据验证未来升级保留契约，以便测试不依赖当前已授权删除的数据。
44. 作为测试者，我希望能够注入 migration 中途失败，以便验证事务和恢复保证。
45. 作为测试者，我希望能够验证 WAL 模式下的备份恢复，以便不会遗漏已经提交的数据。
46. 作为测试者，我希望重复启动不会改变 schema 或业务数据，以便证明生命周期入口幂等。
47. 作为测试者，我希望无效外键写入被拒绝，以便外键配置不仅存在于日志中。
48. 作为发布负责人，我希望 Phase 1 发布前完成干净安装、未来升级和失败恢复验收，以便新数据库底座可以支撑后续阶段。

## Implementation Decisions

- 当前整改前数据库中的全部既有数据均为可删除数据，包括账号、User Plan、训练历史、体测、Template Plan 和其他数据库行；实现不得为保留这些行增加兼容复杂度。
- Phase 1 优先创建干净目标 schema，而不是编写用于迁移当前 44 条外键检查结果及其他脏数据的修复 migration。
- 当前错误外键、`user_id = 0` 和孤儿动作关系通过删除旧结构与数据被清除；不建立 migration quarantine，也不恢复当前孤儿业务记录。
- 需要保留的是产品定义和静态资产，而不是当前数据库行。内置动作、Template Plan 和必要配置应从受版本控制、可审查、可重复生成的种子来源导入目标数据库。
- 种子导入必须可重复且有稳定标识。重复执行不得产生重复动作、重复 Template Plan 或漂移的主外键关系。
- 目标 schema 从第一版开始分离 Template Plan 与 User Plan。Template Plan 使用独立的模板计划、模板动作和模板组结构；User Plan 使用用户计划、计划动作和计划组结构。
- Template Plan 不含真实用户所有权，也不使用 `user_id = 0`。User Plan 必须引用真实用户。
- Template Plan 复制采用深复制，生成独立 User Plan，并复制动作顺序、组数、重量、次数和休息等支持字段；用户编辑不反向影响模板。
- 目标 schema 的新表使用 Plural Table Names。对于仍需保留的旧单数基础表，可在本次干净重建中直接重命名并同步调用方，不需要为旧行提供双读兼容。
- Phase 1 以统一的本地数据库生命周期模块为边界。首次初始化、连接配置、schema 检查、未来 migration、备份、恢复和验证都由该模块编排。
- 生命周期模块提供单一数据库准备入口和结构化结果。结果至少区分：首次初始化、无需迁移、迁移成功、schema 过新、失败且恢复成功、失败且无法恢复。
- 正常业务代码只能获取已被生命周期模块标记为 ready 的连接。
- 本次整改可以执行一次显式破坏性重建，删除 Bundle DB 的旧内容并清理开发环境 Documents DB。该操作必须与未来正式升级路径区分，并在实施记录中明确标记。
- 正式运行路径不得把“数据库缺少新结构”解释为“删除 Documents DB 并复制 Bundle DB”。整改完成后的 Documents DB 是未来真实用户数据的权威副本。
- 强制重建只能存在于明确的整改脚本、测试环境或 DEBUG 工具中；Release 构建的正常启动入口不可调用它。
- 首次安装可以从干净 Bundle DB 初始化 Documents DB，随后仍通过同一生命周期入口验证 schema、ledger 和连接配置。
- schema 版本使用专用 `schema_migrations` ledger，与 App 营销版本、构建号以及旧 `database_version` 记录分离。
- 干净目标 schema 被登记为 migration baseline。之后所有结构或数据演进通过新增、不可变、按序 migration 完成。
- Migration Runner 只执行 ledger 中不存在的 migration。每个 migration 在事务中执行，成功提交后才登记完成。
- 未来 migration 开始前必须创建 SQLite 一致性备份。备份失败时不执行 migration。
- migration 失败时先事务回滚，再恢复升级前备份并验证可打开性。恢复失败时阻止正常业务读写。
- 不支持正式数据库 down migration。schema 高于当前 App 支持版本时保留数据库不变并返回不兼容状态。
- 所有正常业务连接统一执行 `foreign_keys = ON` 和 `busy_timeout = 5000`。
- WAL 是正常运行的目标 journal mode。备份与恢复必须使用 SQLite 一致性快照能力，或在受控 checkpoint/关闭连接后处理完整文件集，不能仅盲目复制主 `.db` 文件。
- 生命周期入口必须串行化首次初始化和 migration，避免多个启动调用者并发复制、重建或迁移数据库。
- ready 门槛至少包括：数据库可打开、目标 migration 已登记、integrity check 通过、foreign key check 无违规、必要表和索引存在、种子导入验证通过。
- 目标 schema 应补齐用户计划所有权、模板筛选、训练历史明细等高频关系索引。
- 生命周期诊断记录数据库路径、schema version、foreign key 状态、journal mode、migration 前后版本、耗时和恢复结果；不得记录敏感业务内容。
- Phase 1 的执行顺序为：定义目标 schema 与种子来源；实现一次性重建；统一连接配置；移除正式整库覆盖路径；建立 migration baseline 与 runner；完成 Template Plan/User Plan 分离；补齐未来升级、备份恢复和启动诊断。
- 本阶段允许建立最小 XCTest target 和数据库 fixture 工具，以验证生命周期入口。完整 CI 和全仓测试体系仍属于后续质量阶段。

## Testing Decisions

- Phase 1 采用一个主要测试接缝：本地数据库生命周期入口。测试输入为 Bundle DB/种子来源、临时 Documents 目录和可选的合成旧 schema；输出为结构化准备结果及可用数据库。
- 测试只断言外部行为：数据库 readiness、schema、业务可读写结果、数据保留契约和恢复保证；不锁定私有 helper、文件布局或内部 SQL 调用次数。
- 所有测试在临时隔离目录中运行，不访问真实 Documents DB。
- 干净重建测试：输入当前不合格数据库或任意旧内容，执行明确的一次性整改重建后，旧行全部不存在，目标 schema、索引和种子内容正确。
- 当前数据删除测试不要求保留任何旧账号、User Plan、历史或体测记录；这些记录应明确不存在于重建结果中。
- 种子确定性测试：从同一受版本控制来源重复生成数据库，内置动作和 Template Plan 的稳定标识与关系一致，不产生重复数据。
- 首次安装测试：Documents DB 不存在时，生命周期入口从干净 Bundle DB 初始化，建立 ledger、配置连接、完成验证并返回 ready。
- 当前版本测试：Documents DB 已处于目标 schema 时不执行重建或重复 migration，也不改变合成用户数据。
- 未来升级测试：使用测试生成的合成用户、User Plan、训练历史和体测数据，从 baseline schema 升级到下一测试 schema；升级后代表性对象、关联和字段仍可通过公共读取能力访问。
- 合成 fixture 是未来数据保留契约的依据；不得把当前已授权删除的数据库行重新变成兼容要求。
- Template Plan 测试：目标模板结构不包含 `user_id = 0` 语义，模板列表可读。
- 模板复制测试：复制后生成真实用户拥有的 User Plan；修改副本后 Template Plan 保持不变。
- 外键测试：ready 连接的 `foreign_keys` 已开启，`foreign_key_check` 无违规，无效关系写入被拒绝。
- 连接配置测试：验证 `busy_timeout = 5000` 和目标 journal mode 应用于所有业务连接。
- WAL 备份恢复测试：在 WAL 场景中写入并提交合成用户数据，创建一致性备份、注入 migration 失败并恢复，确认最近提交数据仍可读。
- 备份失败测试：注入备份失败，确认 migration 未开始且原数据库未变化。
- migration 中途失败测试：确认事务未提交、失败 migration 未写入 ledger，并成功恢复原数据库。
- 迁移后验证失败测试：即使 SQL 执行结束，只要 integrity、外键或必要 schema 验证失败，也不得返回 ready。
- 恢复失败测试：返回不可恢复状态，且不开放正常业务写入。
- 幂等测试：已迁移数据库重复执行生命周期入口，ledger、schema、种子数据和合成用户数据保持不变。
- schema 过新测试：不执行 down migration、不覆盖数据库并返回明确不兼容结果。
- Release 路径保护测试：正常启动路径不存在自动破坏性重建或整库覆盖能力。
- DEBUG/整改重建测试：破坏性重建必须显式调用，不会被普通启动自动触发。
- 诊断测试：必要字段存在，并确认日志不含密码、验证码或用户训练明细。
- 手动回归沿用 Phase 0 清单。重建后至少验证启动、注册/登录、浏览与复制模板、创建和编辑 User Plan、开始与完成训练、查看历史、新增体测。
- 当前仓库没有成熟的自动化数据库测试先例，因此本阶段建立最小集成夹具；该夹具后续可复用于 Repository 和 UseCase 测试。

## Out of Scope

- 不保留或迁移当前整改前数据库中的任何账号、User Plan、训练历史、体测或其他业务行。
- 不逐条修复当前 44 条外键检查结果。
- 不为当前 `user_id = 0` Template Plan 编写兼容迁移。
- 不恢复当前缺失动作造成的孤儿关系，也不建立 quarantine。
- 不处理 Supabase、远端数据库或云端同步迁移。
- 不整体重写 App，也不创建替代项目。
- 不在本阶段完成全部 View、ViewModel、UseCase 和 Repository Protocol 重构。
- 不重做计划、训练、历史或体测 UI。
- 不实现完整 CI、覆盖率门槛或 UI 自动化测试。
- 不提供生产数据库的向下迁移。
- 不实现用户可操作的数据库备份管理或云备份界面。
- 不处理本地凭证加密和客户端邮件密钥等 Security and Privacy Stage 内容。
- 不实现历史分页、统计口径调整或训练状态机重构。

## Further Notes

- 本 spec 覆盖 Phase 1 的 Ticket 1.1 至 Ticket 1.5。
- 2026-07-20 已确认：当前项目数据库中的全部数据在整改需要时可以删除，无需保留。后续实现与评审不得再把当前数据兼容迁移当作验收条件。
- “当前数据可删除”不等于允许未来正式版本继续整库覆盖。Phase 1 仍必须移除生产升级中的破坏性复制路径，并建立未来真实用户数据的 migration 保护机制。
- Phase 0 的数据库基线继续作为问题证据和重建前后对比材料，但不作为数据保留 fixture。
- 目标数据库的静态产品内容应来自可审查的种子来源，而不是当前数据库行。
- Template Plan 与 User Plan 的稳定目标模型是后续 Layered App Flow、Repository Adapter 和计划域整改的前置条件。
